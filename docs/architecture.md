# Magnitide architecture

Magnitide is an ebook library manager: a faster, redesigned alternative to
calibre that imports calibre libraries, runs calibre's plugins and its own,
and serves a library on the local network the way calibre's Content Server
and Calibre-Web do (a headless server is planned).

This document records how the pieces fit and why. Decisions are summarised
at the end with their dates; change them deliberately, and update this file
when you do.

## Goals

- **Fast on large libraries** (50k+ books): native core, virtualized UI.
- **Cross-platform desktop** (macOS, Windows, Linux).
- **Works without calibre**, while respecting people's existing calibre libraries.
- **Can run headless** on a NAS or in a container (planned).
- **Extensible, two ways.** calibre's own plugins run unchanged, in the
  user's installed calibre, in a calibre Magnitide downloads, or in Estuary,
  Magnitide's compatibility layer (no calibre install needed), so people don't
  lose the plugins they rely on by switching. Magnitide's own plugins are
  WebAssembly components on a defined API, sandboxed by construction, so new
  functionality doesn't cost security, and they work the same on a server.

## Components

```
crates/
  catalog          magnitide-catalog: the in-memory book model, search and sort. Every kind of
                   library loads into a Catalog, so views work the same for all of them.
  calibre-compat   Read-only access to calibre libraries (metadata.db + folders). No writes.
  core             magnitide-core: the native library (schema, migrations, queries, edits,
                   import pipeline), EPUB write-back, e-reader detection and matching.
                   No Tauri dependency.
  sources          magnitide-sources: metadata lookup (Open Library, Google Books). Network
                   only on request; results ranked by plain string matching.
  app              Desktop app (Tauri 2). Thin commands over core; the cover:// protocol.
    ui/            Solid + TypeScript + Tailwind v4. Talks to the backend only via api.ts.
  plugins          magnitide-plugins: calibre plugins, through one of three hosts behind one
                   JSON-lines protocol: the installed calibre (calibre-debug), a calibre
                   Magnitide downloads, or Estuary, Magnitide's compatibility layer (CPython +
                   PyQt6, downloaded once, with a calibre compatibility package: `python/`, embedded).
  plugins-wasm     magnitide-plugins-wasm: Magnitide's own plugins, WebAssembly components on
                   the magnitide:plugin API, run by wasmtime in a sandbox; the .mgp package
                   format; the `mgp` tool to check and run a package without the app.
  plugin-sdk       magnitide-plugin-sdk: the API's WIT definitions (`wit/`) and the Rust
                   bindings and helpers for writing a plugin.
  server           magnitide-server: the library over HTTP, read-only: a plain web page
                   for e-reader browsers, an OPDS catalogue and KOReader progress sync. Used
                   by the app today (Settings › Library Server); the headless server will
                   build on it.
plugins/           Magnitide plugins written in Rust, each its own crate: the template, the
                   Open Library example and the Goodreads port.
scripts/           build-plugin.sh and new-plugin.sh; estuary/ builds and fetches
                   Estuary, which CI publishes as estuary-v<N> releases; calibre-release/ pins
                   the calibre release Magnitide can download.
```

Rules that keep this layering useful:

- **Business logic lives in `core`**, not in Tauri commands or HTTP handlers.
  Commands and handlers parse input, call core, and shape output.
- **`ui/src/api.ts` is the only way the UI reaches the backend.** Types for
  every command come from the Rust structs (ts-rs, regenerated by `cargo
test`). A web build swaps the Tauri transport for HTTP without touching
  components.
- **`calibre-compat` never writes** to a calibre library.

## The library

### Native format

A Magnitide library is a folder:

```
My Library/
  magnitide.db                 SQLite database (WAL mode)
  Ursula K. Le Guin/
    The Dispossessed (42)/
      The Dispossessed - Ursula K. Le Guin.epub
      cover.jpg
```

- **Human-readable layout** (`Author/Title (id)/`), like calibre's, so the
  files stay usable without the app. The id suffix keeps folder names unique.
- **Schema versioned with numbered migrations** (`PRAGMA user_version`).
  Each migration runs once, in a transaction; the app refuses to open a
  library newer than it understands rather than guessing.
- **Multi-user-ready from day one.** Personal data (rating, reading status,
  progress; later shelves and annotations) is keyed by user. The desktop app
  uses a single built-in "local" user; the server will add real accounts.
  Library-wide data (title, authors, tags, files) is shared.
- **Provenance is recorded** for imported books (source, source library id,
  source book id, original uuid), so imports can be repeated or reconciled
  and devices that key on uuids keep working.
- **One writer per library.** An open library holds an exclusive OS lock on
  `.magnitide.lock` (released automatically if the process dies); a second
  process gets a "library in use" error naming the holder. SQLite and file
  locks aren't reliable over SMB/NFS, so the app warns when a Magnitide
  library is on a network share (macOS, Linux; Windows UNC paths). Remote
  access goes through the server, not a mounted share.
- **Paths on disk come only from the database.** Requests from the UI or the
  network name a book id (and maybe a format), never a path.
- **Custom fields** (`custom_fields`, `custom_values`) are user-defined
  fields with a key (`#pages` in search), a kind fixed once made (text,
  long text, number, yes/no, date, rating, choice, series) and typed values;
  calibre's custom columns map onto them on import. **Shelves** (schema v4)
  are Magnitide's own collections, and **series** stay calibre-shaped (one
  main series and number on the book) with Magnitide-only additions for
  omnibus ranges, further series and omnibus contents (schema v3), so files,
  devices and import work unchanged.
- **Metadata can be written back into book files** (EPUB and KEPUB for now),
  on request or optionally on every save. Only the OPF's `<metadata>` is
  regenerated; the rest of the OPF and every other zip entry are kept byte
  for byte (copied without recompressing), and elements Magnitide doesn't
  manage, including the package's unique identifier, survive. The new file
  is written beside the original, read back, then renamed over it. Files are
  rewritten only when they differ from the library, because a rewrite changes
  the fingerprint some reading-progress sync keys on;
  `files.metadata_written_at` records when a file last matched.

### calibre libraries

- **Browse read-only.** Opening a calibre library shows it as-is and never
  writes to it. Adding or editing offers to import it first.
- **Import** creates a Magnitide library from a calibre one. Files are
  copied, using copy-on-write clones where the filesystem supports them
  (APFS, Btrfs, XFS), so an import costs little disk space. The calibre
  library is left untouched; people can keep using calibre.
- **Export to calibre** writes a fresh calibre library from a Magnitide one,
  for tools that need calibre's format (Calibre-Web, calibre's Content
  Server, KOReader's calibre plugin). Writing a new `metadata.db` is far
  safer than editing calibre's live database, which needs calibre's custom
  SQL functions, triggers and schema upgrades. The writer
  (`calibre_compat::write`) exists and backs calibre plugins' shadow library;
  a user-facing export is still planned.

## Books in and out

- **Adding books** is a pipeline in `core::import`: detect the file's format
  → plugin hooks (`core::hooks::ImportHooks`, which may hand back a
  rewritten file) → read metadata (EPUB and MOBI/AZW3 natively, a plugin
  reader through `core::hooks::MetadataPlugins` for other formats, the file
  name filling gaps) → store. A new format of a book already in the library
  joins that book.
- **Find Metadata** (`sources`): Open Library and Google Books on request
  only, plus every enabled metadata-source plugin of either kind, asked at
  once; records are grouped into matches (same ISBN, or same title and first
  author) and ranked against the lookup, and the dialog offers the result
  field by field, series included. Covers are proxied through Rust
  (`cover://remote/`) so the webview never fetches from the network.
- **Conversion**: EPUB → KEPUB (Kobo spans in the original bytes) and
  EPUB → AZW3 (a native port of calibre's KF8 writer) are built in; other
  formats go through an installed calibre's `ebook-convert`, run as a
  separate program on copies. A format converted for a device is added to
  the book when the library is a Magnitide one.
- **E-readers** (Kobo, Kindle, calibre-managed USB devices) are found by
  polling mounted volumes and recognised by their folders; their files are
  matched to books by calibre's uuid, ISBN, identical file, then title and
  author. Sending chooses the format the device reads best, converting on
  the way when needed; shelves become collections on a Kobo (for Kobo's app
  and KOReader, after a backup); a device's other files can be added to the
  library. MTP devices aren't supported yet.
- **Jobs**: longer work (sends, conversions, adding, deleting, plugin runs)
  runs as jobs shown in the status bar and kept in a session-only history.
  What a job changed is in the library already; the history is the account.

## Library server (in the app)

Settings › Library Server serves the open library on the local network while
the app runs. It's off until turned on, and the library is read-only to it by
construction: the `server` crate only reads a `Catalog` and the library's
files (through a `Source` trait asked on every request, so it follows
whichever library is open), and the catalogue only answers GET and HEAD. The
one thing it writes is KOReader reading positions, in their own database.

- **Web page** for e-reader browsers (Kobo's beta browser is old WebKit):
  server-rendered HTML, no scripts, black on white, no flexbox `gap`.
  Descriptions go through the same sanitizer as the app. Kobo's browser (by
  its user agent) is offered KEPUB first, converted from the EPUB on demand
  and cached outside the library.
- **OPDS 1.2** at `/opds`: navigation feeds for shelves, authors and series,
  acquisition feeds for books, OpenSearch, 25 books a page.
- **Password** (optional): HTTP Basic, any user name, compared in constant
  time. Plain HTTP on a home network, so it keeps out housemates, not
  eavesdroppers.
- **KOReader progress sync** (`kosync`): koreader-sync-server's protocol
  (`/users/auth`, `/users/create`, `PUT /syncs/progress`,
  `GET /syncs/progress/<document>`, `/healthcheck`), so KOReader's custom
  sync server can be Magnitide. KOReader signs in with its own headers
  (a user name and the MD5 of a password), not Basic auth: with a server
  password, any user name and that password; without one, open. User names
  only keep people's positions apart. Positions live in
  `reading-positions.sqlite` in the app's data folder, never in a library,
  keyed by user name and KOReader's document fingerprint
  (`core::fingerprint::partial_md5`, checked against KOReader's own value).
- **Positions reach the library** (`core::positions`): the library keeps
  the fingerprints a book can be known by: its own files' (taken when first
  needed, again when a file's mtime changes, in `files.fingerprint`) and
  those of copies that left it (`file_copies`): a copy sent to a device has
  metadata written in, a download made for a Kobo is a fresh KEPUB, so each
  differs from the library file's. The `server` crate reports each download
  (`Served::copy_served`) and each saved position (`Source::position_synced`)
  to whoever serves the library; the app matches the position at once, and
  every stored position again when a library opens. A match moves the local
  user's `user_books` row on (status, progress, `last_read_at`, `device`)
  only when the position is newer than the last one the library saw, so the
  app's own comic reader and several readers don't fight; at 100% the book
  is read. The UI holds reading states beside the catalog (like device
  matches), not in `Book`, so the 25 places that build one are untouched.
- tiny_http with four worker threads. The address shown comes from the
  network adapters, skipping VPN tunnels and virtual adapters (point-to-point,
  /32, or tunnel-like names): with a VPN up, the default route's address is
  the tunnel's, which devices on the Wi-Fi can't reach.

## Server mode (planned)

A `magnitide-server` binary over `core`, shipped as a small Docker image for
NAS use: map a port and a library folder.

In order of value for effort:

1. Web UI (the same Solid app over HTTP), and the `server` crate's OPDS
   catalogue and e-reader page, which the desktop app already serves.
2. **Accounts**: authentication, per-user state, rate limiting. TLS is
   expected from a reverse proxy; the docs will show how.
3. **KOReader progress sync**: the protocol and the matching of positions to
   books are done (the desktop app serves it); a server adds real accounts
   and per-user libraries.
4. **Kobo sync** (the feature many Calibre-Web users rely on).
5. calibre's wireless-device protocol, so KOReader's "Calibre" plugin can
   connect.

The desktop app may later connect to a server as a client instead of opening
a library file directly.

## Extensibility

- **Extension points are Rust traits**, so both plugin systems plug in
  where first-party code does and `core` knows nothing about either
  runtime: `core::hooks::ImportHooks` (file types to accept, a hook on each
  file added) and `core::hooks::MetadataPlugins` (readers and writers for
  formats) are implemented by the calibre host and the WebAssembly host
  alike, and the app fans each call out to both (Magnitide's plugins first);
  metadata sources join the `sources` fan-out in Find Metadata; library
  actions get the open library through `plugins-wasm`'s `LibraryAccess`,
  which the app implements over core's own edit paths. Export formats and
  sync protocols as traits are still to come with server mode.
- **Both plugin systems are listed and managed in one place**, Settings ›
  Plugins, with the same enable, remove and log affordances; one plugins
  submenu in the book menu and one Plugins button carry both kinds' menus.
- **calibre plugins** run unchanged (`magnitide-plugins`) in one of three
  hosts behind one JSON-lines protocol, chosen in Settings: the user's
  installed calibre (`calibre-debug` running Magnitide's host package on
  calibre's own code), a calibre release Magnitide downloads (pinned
  version and calibre's published SHA-512, calibre's GitHub release first
  and its own server second), or Estuary, Magnitide's compatibility layer (CPython 3.14, a
  stripped PyQt6 and a few wheels, built by CI, hash-pinned in the app,
  downloaded once) with a `calibre` compatibility package written for
  Magnitide (the loader, `calibre.db` on a shadow library, `Metadata`,
  config, ICU-style collation, jobs, the GUI classes), backed by Magnitide's
  library and a stand-in for calibre's main window. The installed calibre is
  the oracle the compat package is tested against; fixes flow between the
  tracks. Plugin settings live in Magnitide's folder
  (`CALIBRE_CONFIG_DIRECTORY`), never calibre's. Metadata sources are asked
  in Find Metadata; GUI plugins run on a calibre-format shadow of the open
  library, and what they change is applied back through Magnitide's edit
  path; file-type plugins, metadata readers and writers plug into
  `core::hooks`; preferences and library-closed plugins run too. The
  survey, the design and what each plugin type gets are in
  [calibre-plugins.md](calibre-plugins.md).
- **Magnitide's own plugins** are WebAssembly components on the
  `magnitide:plugin` WIT API (`crates/plugin-sdk/wit`), run by
  `crates/plugins-wasm` in wasmtime: sandboxed (no filesystem or network
  unless the manifest's capabilities grant it, a memory cap, a deadline per
  call, a fresh instance per call), language-agnostic, and the same on a
  server. Packaged as `.mgp` (a zip with `manifest.toml` and the
  component). Four kinds, each a world a plugin implements: metadata
  sources, import hooks, file-metadata plugins (readers and writers) and
  library actions. The middle two are the same `core::hooks` traits the
  calibre host implements, with the file handed in through a per-call
  sandbox (`/in` read-only, `/out` scratch); library actions read, search
  and edit the open library through capability-gated host functions, report
  progress to the job bar and can ask the user mid-run (the wait credited
  back to their deadline). A Rust SDK, a template with a skeleton of each
  kind, the `mgp` tool and two sources (Open Library, and the calibre
  Goodreads plugin ported) are in the repository. The calibre host stays for
  everything that leans on calibre's GUI and library; lighter plugins port
  to the native API with far less code. See [plugin-api.md](plugin-api.md).

## Security principles

- calibre libraries are opened read-only; the native library is the only
  thing Magnitide writes.
- Book descriptions are sanitized HTML (ammonia) before reaching the UI.
- The UI runs under a strict Content Security Policy; links in book content
  never navigate the app window.
- Only database-derived paths are ever read, opened or revealed.
- The network is only used on an explicit action (metadata lookup, the
  library server, plugin downloads); the webview itself never contacts
  third-party hosts.
- Magnitide plugins can do only what their manifest declares and the host
  links: no filesystem or network by default, each call a fresh instance
  with a memory cap and a deadline, and a crash a plugin error rather than
  an app crash. Capabilities are shown when a plugin is added.
- calibre plugins run in a separate process (the host) that Magnitide can
  stop; what they download (Estuary, a calibre release) is
  checked against hashes compiled into the app or published by calibre
  before it's installed, and installs are atomic.
