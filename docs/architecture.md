# Magnitide architecture

Magnitide is an AI-free ebook library manager: a faster, redesigned
alternative to calibre that can import calibre libraries and, later, serve
them on a network the way calibre's Content Server and Calibre-Web do.

This document records how the pieces fit and why. Decisions are summarised
at the end with their dates; change them deliberately, and update this file
when you do.

## Goals

- **No AI features.** No LLM integrations, cloud or local.
- **Fast on large libraries** (50k+ books): native core, virtualized UI.
- **Cross-platform desktop** (macOS, Windows, Linux). Mobile is out of scope.
- **Works without calibre**, while respecting people's existing calibre libraries.
- **Can run headless** on a NAS or in a container (planned).
- **Extensible** through plugins (planned).

## Components

```
crates/
  catalog          magnitide-catalog: the in-memory book model, search and sort. Every kind of
                   library loads into a Catalog, so views work the same for all of them.
  calibre-compat   Read-only access to calibre libraries (metadata.db + folders). No writes.
  core             magnitide-core: the native library (schema, migrations, queries, edits,
                   import pipeline). No Tauri dependency.
  app              Desktop app (Tauri 2). Thin commands over core; the cover:// protocol.
    ui/            Solid + TypeScript + Tailwind v4. Talks to the backend only via api.ts.
  server           (planned) Headless HTTP server over core: web UI, OPDS, sync APIs.
```

Rules that keep this layering useful:

- **Business logic lives in `core`**, not in Tauri commands or HTTP handlers.
  Commands and handlers parse input, call core, and shape output.
- **`ui/src/api.ts` is the only way the UI reaches the backend.** Types for
  every command come from the Rust structs (ts-rs, regenerated by `cargo
  test`). A web build swaps the Tauri transport for HTTP without touching
  components.
- **`calibre-compat` never writes** to a calibre library.

## The library

### Native format

A Magnitide library is a folder:

```
My Library/
  magnitide.db                 SQLite database (WAL mode)
  Ursula K. Le Guin/
    The Dispossessed (42)/
      The Dispossessed - Ursula K. Le Guin.epub
      cover.jpg
```

- **Human-readable layout** (`Author/Title (id)/`), like calibre's, so the
  files stay usable without the app. The id suffix keeps folder names unique.
- **Schema versioned with numbered migrations** (`PRAGMA user_version`).
  Each migration runs once, in a transaction; the app refuses to open a
  library newer than it understands rather than guessing.
- **Multi-user-ready from day one.** Personal data (rating, reading status,
  progress; later shelves and annotations) is keyed by user. The desktop app
  uses a single built-in "local" user; the server will add real accounts.
  Library-wide data (title, authors, tags, files) is shared.
- **Provenance is recorded** for imported books (source, source library id,
  source book id, original uuid), so imports can be repeated or reconciled
  and devices that key on uuids keep working.
- **One writer per library.** SQLite must not be shared over SMB/NFS: two
  machines writing one file over a network share is a known corruption
  risk. Remote access goes through the server, not a mounted share. The app
  will warn when a library is opened from a network volume.
- **Paths on disk come only from the database.** Requests from the UI or the
  network name a book id (and maybe a format), never a path.

### calibre libraries

- **Browse read-only.** Opening a calibre library shows it as-is and never
  writes to it. Adding or editing offers to import it first.
- **Import** creates a Magnitide library from a calibre one. Files are
  copied, using copy-on-write clones where the filesystem supports them
  (APFS, Btrfs, XFS), so an import costs little disk space. The calibre
  library is left untouched; people can keep using calibre.
- **Export to calibre** (planned) writes a fresh calibre library from a
  Magnitide one, for tools that need calibre's format (Calibre-Web, calibre's
  Content Server, KOReader's calibre plugin). Writing a new `metadata.db` is
  far safer than editing calibre's live database, which needs calibre's
  custom SQL functions, triggers and schema upgrades.

## Server mode (planned)

A `magnitide-server` binary over `core`, shipped as a small Docker image for
NAS use: map a port and a library folder.

In order of value for effort:

1. Web UI (the same Solid app over HTTP) and **OPDS** catalogues, which
   KOReader and most reading apps can browse and download from.
2. **Accounts**: authentication, per-user state, rate limiting. TLS is
   expected from a reverse proxy; the docs will show how.
3. **KOReader progress sync** (kosync protocol).
4. **Kobo sync** (the feature many Calibre-Web users rely on).
5. calibre's wireless-device protocol, so KOReader's "Calibre" plugin can
   connect.

The desktop app may later connect to a server as a client instead of opening
a library file directly.

## Extensibility

- **Extension points are Rust traits in `core`** from the start: import
  hooks, metadata sources, export formats, sync protocols. Built-in features
  (OPDS, kosync, Kobo sync) are implementations of these traits, so
  third-party code plugs in where first-party code does.
- **Import is a pipeline** with hook points: detect file → plugin hooks →
  read metadata → store. calibre's `FileTypePlugin` maps here.
- **Third-party plugins** (later) run as WebAssembly modules (sandboxed,
  language-agnostic, safe on a server) once the traits have settled.

## Security principles

- calibre libraries are opened read-only; the native library is the only
  thing Magnitide writes.
- Book descriptions are sanitized HTML (ammonia) before reaching the UI.
- The UI runs under a strict Content Security Policy; links in book content
  never navigate the app window.
- Only database-derived paths are ever read, opened or revealed.
